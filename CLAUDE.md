# Code Style

## Comments

- Don't use one line "//" comments unless the code is very strange. Comments are usually not needed.

## Unit Tests

- Do not prefix any variables or constants with test... or TEST_... or anything similar. We are in a test, so it is already obvious that these are test values.

## Dependency Injection

- Avoid `@Autowired` member variables - prefer constructor injection
- For normal classes that need to be part of the dependency graph, annotate them with `@Component`
  - `@Service` can be used if the class' name ends in "Service"
- In cases where an explicit constructor is needed, implement it.

## Retrofit Services

- When generating API services. Use Retrofit.
- When generating API request and response objects, declare the classes in separate files.
- Data classes declared for APIs should
    - Be declared in their own files
    - Not be nested classes
    - Use `@JsonProperty` on every member variable - Use any information you have in order to determine this value.
    - Use any information you have to inform the nullability of any member variables

## Variable Names
- Avoid the use of acronyms except for very common ones such as Http
- Do not truncate words in variable names. E.g. prefer "address" over "addr"

## Constants
- Avoid the use of "Magic Numbers" and "Magic Strings". Favor using private static final constants declared at the top of the class.
- Declare format Strings such as date/time formats or currency formats as private static final constants.

## Margins and Line Lengths
- We use 140-line margins in Kotlin
  - Only test classes are permitted to exceed this margin
  
## Nested Method Calls
- Avoid nesting method calls. Where possible, assign the inner method call to a variable, and then pass the variable into the outer method call instead.

# Git
- Never co author commits
- Never write anything similar to "Generated by..." or "Co-authored by..." or anything like that
- Commit messages must be one line only, and written in the imperative tense.
